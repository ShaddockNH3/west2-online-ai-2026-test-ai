## 数据与场景

- 数据：3 个商品、4 个 SKU、徽章库存 100；限量活动配额 50，每人限购 2；40 个压测用户各有一条地址。

- 场景二 集中抢购：40 个用户同时 `POST /activities/{id}/flash-sale`，各抢 1 件。分别记录受理响应和最终建单结果。

## 瓶颈与改动

看服务端日志，一次抢购要在一个写事务里跑约 10 条 SQL：查活动、查活动 SKU、
查 SKU 与商品、查地址、统计已购数量、更新名额、查库存、更新库存、
写库存流水、写抢购申请、写任务。SQLite 同一时刻只允许一个写事务，
持有时间越长，后面排队的请求等得越久。

按「先减语句数、再减持锁时间」的思路改了四处：

1. 鉴权：会话和用户从两次查询合并成一条 join，每个受保护请求少一次往返。
2. 秒杀：活动和活动 SKU 合并成一条 join，少一次查询。
3. 库存：`UPDATE ... RETURNING available` 直接拿更新后的值，省掉单独 SELECT；
   MySQL 不支持 RETURNING，保留 `rowcount` 的兜底分支。
4. 连接初始化：`PRAGMA journal_mode` 改为建表时设一次（它是写进库文件的持久设置），每条新连接只设 `busy_timeout`、`foreign_keys`、`synchronous`。

复测条件完全一致（重置数据、同样 40 用户 20 并发）。

## 失败与恢复

以下场景由自动化测试覆盖，不是压测结论：

- 物流发货失败：返回 502，履约单记录 `attempts` 与原因，再点一次发货即可成功。
- 后台任务失败：退避重试 3 次后置为 FAILED，管理端可查原因并重新排队。
- 进程重启：停留在 RUNNING 的任务按 `locked_at` 超时捞回，未完成订单继续处理。
- 并发超卖：3 件库存 5 个用户同时下单，恰好 3 单成功；8 个用户抢 3 个名额同理。

## MySQL 对照

同一台机器、同样的脚本与参数，把 `SHOP_DATABASE_URL` 换成 Docker 里的 MySQL 8.4 再跑一次：

| 指标 | SQLite | MySQL 8.4（Docker Desktop） |
| --- | --- | --- |
| 浏览吞吐 | 94.9 req/s | 83.6 / 146.7 req/s（两次波动大） |
| 浏览 P95 | 365 ms | 249 / 606 ms |
| 抢购 40 并发、全部受理 | 27.3 req/s，P95 1270 ms | 21.4 req/s，P95 1781 ms |
| 抢购 40 并发、配额 5（35 个直接拒绝） | — | 90.3 req/s，P95 413 ms |
| 超卖 | 无 | 无 |

结论有点反直觉：**换 MySQL 并没有更快**。SQLite 用 WAL + `synchronous=NORMAL`，
小事务提交不强制刷盘；MySQL 默认 `innodb_flush_log_at_trx_commit=1`，每次提交都落盘，
再加上 Docker Desktop 的 I/O 与网络虚拟化，单进程下的小事务反而更贵。

所以前文「单写锁是瓶颈」的说法要修正得更准确：锁等待确实存在，但主要成本是
「一个抢购请求 = 一个多语句事务 + 一次提交」，以及单进程事件循环。
真要往上走，方向是改架构——批量受理、异步落库、多进程加连接池，
而不是换一个数据库。配额售罄后事务变短，MySQL 立刻回到 90 req/s，也印证了这一点。

## Redis 缓存对照

商品列表和详情接上 Redis 缓存后（同一台机器、20 并发 8 秒、同一份数据）：

| 指标 | 无缓存 | Redis 缓存 |
| --- | --- | --- |
| 请求数 | 1717 | 2180 |
| 吞吐 | 213.1 req/s | 271.2 req/s |
| P50 | 64.3 ms | 41.9 ms |
| P95 | 255.6 ms | 229.3 ms |
| P99 | 423.8 ms | 525.9 ms |

吞吐涨 27%，P50 降 35%。P99 反而变差（424 → 526 ms），因为慢请求里多了一次 Redis 往返，
最坏路径变长；要压 P99 得加进程内二级缓存或把 TTL 拉长。

一致性靠版本号：管理员改类目/商品/SKU/活动/库存时 `INCR` 版本号，缓存 key 里带版本，
旧 key 不再被读、等 TTL 过期回收。实测改价后商品详情立刻反映新价格。
下单不会主动失效缓存，所以列表里的库存数字最多滞后 20 秒。

## 遗留问题

- 40 并发抢购 P95 在 1.3–1.8 s 之间，瓶颈是多语句事务的提交成本，换 MySQL 没有解决。
- 商品浏览 84–147 req/s，主要成本在反序列化与多次查询，没做缓存；
  如果选「热门商品详情」专项，这里才是该上缓存的地方。
- 压测端与服务端同机，客户端本身也占 CPU；Docker 场景多一层网络与文件系统虚拟化，
  真实吞吐应以多机压测为准。
- 容器里只跑 1 个 uvicorn worker，多进程与连接池参数没有调优。
