# 这一份作业里遇到的问题

按题目要求，记录实际卡住过的地方和处理方式。

## 1. 好感度阈值和对话轮数对不上

结局线定在好感度 100，但 5 轮对话每轮最多加 16，全部答对也只有 69，
光靠聊天永远到不了结局，只能一遍遍重复最后一句话。

问题出在「先定了阈值，再随手填加成」，两边的数值没有互相校核。

处理方式是把它当成一道算术题：5 轮对话 69 分，剩下的靠送礼补。
每份对胃口的礼物 +10 到 +20，送两三次正好过线。
这个平衡是用脚本喂输入跑出来的，比手点快得多：

```zsh
printf '1\n1\n1\n1\n1\n1\n1\n1\n' | python main.py
```

一路选「1」，看最后停在多少分，就能反推阈值是否合理。
现在实测是第 7 次聊天触发结局（前 5 轮拿满 69，后两轮各 +16）。

## 2. 用管道测试时程序崩在 `EOFError`

想批量测试不同分支，于是这样跑：

```zsh
printf '2\n1\n2\n1\n' | python main.py
```

输入行数不够时，`input()` 读到输入结束就抛 `EOFError`，前面十几行正常输出全被红字盖住。

两种处理都试过：

- **把输入喂够**：能跑，但每改一次流程就要重新数一遍行数，很容易数错；
- **捕获 `EOFError`**：在 `ui.ask_choice()` 里 `except EOFError` 返回 `None`，上层当作退出。

最后选了第二种，因为它顺带解决了「玩家按 `Ctrl + D`」的情况：程序会干净地退出，
而不是甩出一段 traceback。

## 3. 类型注释里的 `object` 陷阱

`story.py` 的场景数据一开始写成：

```python
SCENES: dict[str, dict[str, object]] = {...}
```

看着没毛病，实际用起来很难受：`scene["lines"]` 的类型被推成 `object`，
既不能直接遍历，也拿不到补全，等于注释白写。

改成 `TypedDict` 之后：

```python
class Scene(TypedDict):
    title: str
    lines: list[str]
    prompt: str
    yes: list[str]
    no: list[str]
```

`scene["lines"]` 直接就是 `list[str]`，写错键名编辑器当场标红。

同一类问题还出现在礼物表上：`GIFT_TABLE.get(gift, {})` 返回 `dict[str, int]`，
再 `.get("*", 0)` 才是 `int`。中间漏掉默认值，类型就变成 `int | None`，
后面拿去做加法会报错。

## 4. 从哪个目录运行，其实是有讲究的

把代码拆成四个文件之后，我担心过「从仓库根目录跑会不会找不到 `game` 模块」。
实测是可以的：

```zsh
cd west2-online-ai-2026-test-ai
python foundation/foundation1/assignment2-campus-if-love/main.py
```

原因是直接运行脚本时，`sys.path[0]` 就是**脚本所在目录**，
所以 `from game import Game` 能找到同目录的 `game.py`。

但这不代表随便怎么跑都行：

- 如果改成 `python -m foundation.foundation1.assignment2.main`，起点就变成当前工作目录，
  每层目录都得有 `__init__.py` 才能被识别成包；
- 如果把 `main.py` 挪到子目录、让它在父目录里运行，相对导入就会失效。

结论是：拆分文件之后，「在哪运行」也变成了接口的一部分，得在 README 里写清楚。

## 5. 对话聊完之后怎么办

五轮对话用完，玩家却可能还没到结局（比如一直在送奇怪的石头）。

可选的做法有三个：报错、从头循环、重复最后一轮。

报错太粗暴，从头循环会让玩家发现自己在说重复的话。
最后选的是「重复最后一轮」，并且把最后一轮的加成设得偏高（+16），
让玩家有机会靠它把分数补上去。
这个行为写进了代码注释，也在 `Character.talk()` 里用 `min(self.talk_count, len(dialogues) - 1)` 明确表达。

## 6. 送礼菜单和聊天菜单长得太像

第一版把「送哪个礼物」也做成了二选一，结果七种礼物只能分成两页，很别扭。

后来统一成「编号 + 输入数字」：礼物菜单打印 7 个礼物加一个「算了」，
用 `ui.ask_choice(prompt, len(GIFTS) + 1)` 一次拿到合法值。
这样菜单可以随时加礼物，不用改流程代码。

## 7. 存档 Bonus 的三个坑

### 7.1 快照要包含「进度阶段」，不只是数值

第一版只存了角色的好感度和对话次数，读档之后又从场景一重新问起，
角色线直接被跳过、却又回到了选人界面。

正确做法是把「现在处于哪个阶段」也写进快照：
`stage`（选人 / 角色线 / 已结局）加上 `scene_index`（已经过掉几个场景），
读档时 stage 和 target 都有值就直接进角色线。

### 7.2 读档恢复的是同一个角色对象

`Game.characters` 里的 `Character` 实例在 `Game` 构造时就创建了，
读档只是把快照里的数值**覆盖**到这个对象上（题目提示的「暴力覆盖」）。
一开始想「新建一个 Character 再赋值」，但对话轮数、送礼次数这些字段
分散在对象上，重建反而容易漏字段。

### 7.3 即时存档的写入时机

「每次操作都进行存档」的关键是找对**操作边界**：
聊天一次、送一次礼、查看一次、每经过一个场景，各算一次操作。
把这些边界收拢到 `_story_loop` 的统一出口（`self.autosave()`），
而不是在 `Character.talk()` 里写——存档是游戏流程的事，不是角色的事。
